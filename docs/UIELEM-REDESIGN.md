# UI 元素识别：重新规划

> 这份文档取代 `UIELEM.md` 里所有关于"怎么拿到布局块"的结论。
> `UIELEM.md` 保留为**事实与实现档案**（采集、OCR、内存、实验数据都还在）。
>
> 出发点：用户要的是 PixPin 那种效果——悬停框住**视觉上的一块区域**（一行卡片、整个
> 侧边栏、内容面板），滚轮上下换层级。我们做了五轮都没做到，所以从头梳理。

## 一、结论先行

| 问题 | 答案 | 依据 |
| --- | --- | --- |
| UIA 的 ControlView 能给布局块吗 | **不能** | 卡片往上第一层父级**直接是 Document**，中间全被压平 |
| UIA 的 RawView 能给吗 | **能**，完整层级都在 | `RawViewWalker` 从文本往上爬到 10+ 层 Group，每层都有矩形 |
| 能用 `FindAll(RawView)` 批量拿吗 | **不能** | 357 个 ≈ ControlView 的 380 个，条件只走 provider 过滤，provider 不给 |
| 所以 RawView 只能怎么取 | **必须用 walker 逐层走** | 唯一可行路径 |

**一句话**：PixPin 那种框，在 UIA 里存在于 **RawView 的树**，但我们只能靠 walker 一层层爬，
拿不到"一次性批量结果"。这决定了实现方式，也决定了性能预算。

## 二、已证事实（都是实测，可复现）

### 2.1 ControlView 把层级压平了

`cargo run --example uia_tree -- 900,510`（光标在聊天正文上）：

```text
 0. ctrl       "你说得对，我一直在猜…"   @876,498 285x21
 1. Document   WorkBuddy 资料库          @355,188 1463x1126   ← 直接跳到 Document
 2. Pane       WorkBuddy
 3. Pane       桌面 1
```

**中间什么都没有。** 段落框、消息块、消息列表、滚动容器，一层都不在 ControlView 里。

### 2.2 RawView 里层级完整

`cargo run --example uia_tree -- 900,510 --raw`：

```text
 0. ctrl    "你说得对…"        @876,498   285x21
 1. ctrl                       @876,495   752x53      ← 段落
 2. Group                      @876,370   752x590     ← 消息块
 3. Group                      @876,370   752x590
 4. Group                      @876,-1873 752x2869    ← 消息列表
 5. Group                      @876,-44931 752x46077  ← 虚拟滚动容器
 6. Group                      @696,282   1122x864    ← 主内容区
```

**这就是"包含它的更大元素"的完整链条**，和 PixPin 文档描述的行为一致。

### 2.3 批量接口救不了

同一窗口、同一时刻：

| 视图 | `FindAllBuildCache(Subtree)` 节点数 |
| --- | --- |
| ControlView | 380 |
| RawView | 357 |

条件只是交给 provider 过滤，Chromium 的 provider 本来就只提供控制视图那一棵。
**`FindAll` 这条路走不通，只能 walker。**

### 2.4 其它已验证的事实（别再重复试）

- **提权不影响**：正式版日志里正常采到 607 个元素。
- **桌面根快照拿不到页面内容**：`链接` 只有 1 个（浏览器窗口单独采有 87 个）。
- **冷热一致**：连采两次节点数和耗时几乎相同，不存在"Chromium 懒建树要二次采样"。
- **本地非提权悬停是好的**：`悬停→元素 链接 · 有趣的开源社区 @1902,638`。
- **正式版日志里元素也在命中**：`按钮 · 查看站点信息 @116,48`、`列表项 · 收藏网址`。

## 三、我前面错在哪

| 错误假设 | 怎么错的 | 代价 |
| --- | --- | --- |
| "采不到是因为只采前台窗口" | 部分对（任务栏确实如此），但页面上采到了也不出块 | 两轮 |
| "自己造块：等距元素合一行" | 方向错。合出来的框是猜的，不是真实元素；PixPin 给的是真实父容器 | 一轮，已删 |
| "RawView 没用（节点数一样）" | **只比了数量，没比深度**。RawView 的价值在树深度，不在节点数 | 一轮，最关键的误判 |
| "容器被我过滤了（container 缺 List）" | 部分对，但 Chromium 在 ControlView 下根本不吐 List | 一轮 |

## 四、两条可行路线

### 路线 A：RawView 实时爬父链（推荐）

**做法**

1. 悬停时，从光标下的元素开始，用 `RawViewWalker.GetParentElement` 往上爬；
2. 每层过滤"无意义层"：矩形几乎相同、面积小于阈值、不可见的层都跳过；
3. 得到 `[最小元素, 段落, 块, 列表, 面板, 文档, 窗口]` 作为滚轮层级；
4. 难点：**覆盖层会挡住 `ElementFromPoint`**。解法是"在目标窗口自己的子树里做命中"：
   `ElementFromHandle(光标下的窗口)` + walker 逐层找"矩形包含光标的子元素"，
   这条路不经过全局命中测试，覆盖层挡不住。

**代价**

- 每次爬链约 20–50 次跨进程调用，粗估 **50–150ms**。必须做防抖（悬停静止 100ms 才爬）+ 缓存（同一元素不重复爬），否则鼠标一动就卡。
- 实现量约 150–200 行（命中下降 + 父链爬取 + 缓存 + 接线）。

**风险**

- Chromium 的 RawView 里同一块区域有 3–4 层矩形相同的 Group，需要合并，否则滚轮要滚半天。
- 某些 app（Win32 原生）RawView 和 ControlView 差别不大，效果会退化成现在的样子。

### 路线 B：视觉区域检测（截图上的分割）

**做法**：在截图上做区域分割，不依赖任何 app 的 a11y。轻量模型（PP-DocLayout / YOLOX-nano）
或传统 CV（背景色变化 + 边缘 + 矩形拟合）。

**代价**：模型训练/选型/调参，或 CV 规则不稳定；体积与内存（CPU EP 640 输入实测 43ms）。

**收益**：连游戏、Figma、纯 canvas 也能用——这是 UIA 永远做不到的。

### 路线 C：A 为主 + B 兜底

A 覆盖有 a11y 的窗口（绝大多数场景），B 只在 A 拿不到层级时启用。

## 四点五、路线 A 第一步已落地（2026-11-24）

采集从 `FindAll(ControlView)` 换成 **`RawViewWalker` + `GetFirstChildElementBuildCache`**：

* `FindAll` 拿不到层级（条件只走 provider 过滤）；
* walker 能走完整层级，且 BuildCache 版本让**每个节点只一次跨进程调用**；
* 关键坑：cache request **不能设 `AutomationElementMode_None`**——那个模式只给缓存值、
  不给活引用，walker 遍历会直接返回空（实测整棵树只剩根节点）。

实测（WorkBuddy 窗口）：

```text
层级链 5 层：其他[561x864] > 其他[561x1032] > Chrome_RenderWidgetHostHWND[1463x1126] > WorkBuddy > 整块屏幕
按面积排序的容器：561x1032（主内容区）340x1096（侧边栏）561x864 513x134（块）
```

`stack_at` 用几何包含把这些层串起来，滚轮向上就是"更大的元素"。
196 个元素 / 845ms，后台线程，不挡覆盖层。

## 四点六、真正的根因（2026-11-25，三个 bug 叠在一起）

在真实浏览器页面（SenseNova）上跑通之后，找到了三个叠加的 bug：

### bug 1：`IsOffscreen` 在窗口失焦时整页说谎

```text
UIA RawView 采到 129 个 {"offscreen": 1817, ...}   ← 一页 1800+ 个元素全被判"屏幕外"
```

Chromium 在**浏览器窗口没有焦点**时，会把整个页面的元素标记为 offscreen。而截图那一刻
焦点早就不在浏览器上了（可能在 IDE 或终端）。于是整页内容被扔光，只剩几个容器。

**修法**：不信 `IsOffscreen`，只信矩形——`intersects(rect, screen_bounds)` 才是事实。

### bug 2：BFS 深度不够，页面内容根本走不到

页面正文在 `Document` 下面还有 **8–12 层**。原来 `MAX_DEPTH = 14`，从窗口根算根本到不了
内容层，采到的全是外层容器。改成 **32**。

### bug 3：不剪枝，配额被虚拟列表吃光

页面有 8 万多像素高的虚拟滚动容器，`MAX_NODES` 瞬间耗尽，还超时（1635ms → 快照 0 个）。

**修法**：下降前先看父矩形，**完全在屏幕外就整棵子树跳过**。

三处修完：**422 个元素 / 456ms**，页面按钮、文本、容器全部到位。

### 验证（同一台机器、同一个页面）

```text
uia_tree 1200,620（RawView 真实父链）：
  0. ctrl  "message.tool_calls[].id"  341x59
  1. ctrl                              1019x59
  2. ctrl                              1019x631

我们采集后悬停 (1198,619)：
  层级链 4 层：其他[1200x418] > Chrome_RenderWidgetHostHWND > 窗口 > 屏幕
```

## 五、我的建议

**先做 A，但第一步不是写代码，是验证。**

A 成立的前提是：**在浏览器页面上，RawView 的父链确实能产出和 PixPin 一样的一行卡片框。**
这个还没验过——目前只在 Electron（WorkBuddy）窗口上验过层级存在。

验证只要一条命令（浏览器窗口在屏幕上，鼠标先移到那行卡片上）：

```bash
cargo run --release --example uia_tree -- <卡片上的坐标> --raw
```

看输出里有没有一层矩形约等于"整行卡片"（比如 `1361x40`）。有 → A 成立，我按第四节做；
没有（父链直接从卡片跳到 Document）→ A 在那个站点上无效，只能上 B。

## 六、如果 A 成立，里程碑

| 步骤 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 子树内命中（绕开覆盖层）+ 父链爬取 + 同框层合并 | `uia_tree` 在页面上给出 3–6 层合理链 |
| 2 | 接进悬停：防抖 100ms、缓存、滚轮沿链上下 | 悬停不卡，滚轮换层级 |
| 3 | `Tab` 切"只认窗口"；「元素检测边距」设置（−50–999） | 与 PixPin 设置项对齐 |
| 4 | 原生 Win32 应用回归（RawView 差异大，需要降级策略） | Office/资源管理器/IDE 都可用 |

## 七、什么时候该放弃 A 转 B

* 三个不同类型的网站（导航站、电商、后台系统）里有两个爬不出中间层；
* 爬链耗时稳定超过 150ms，防抖也压不住；
* 或者用户主要截的是游戏/设计软件（本来就没 a11y）。

这三条任意一条成立，就把 A 降级成"能爬就爬、爬不到就用窗口"，把预算转到 B。
