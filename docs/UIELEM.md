# UI 元素识别（uielem）

> **⚠ 关于"布局块/层级"的结论以 [`UIELEM-REDESIGN.md`](UIELEM-REDESIGN.md) 为准。**
> 本文档里"视觉通道砍掉""几何聚合造块""container 补 List 就够了"这些说法，
> 在实测 ControlView/RawView 之后已经被推翻：布局层级**只存在于 RawView**，
> 而 RawView 只能靠 walker 逐层走。采集、OCR、内存、实验数据部分仍然有效。

截图场景下自动识别界面里的 UI 元素（按钮、输入框、图标、文本区域），并顺带把 OCR 的
准确率拉起来。模块：`crates/capture/src/uielem.rs`；探针：`cargo run --example ui_scan`。

## 结论

**能实现，而且不需要训练模型就能覆盖主流场景。** 核心不是"找个模型看截图"，而是
**UIA 通道为主、OCR 通道补文本、视觉模型只在自绘 UI 上兜底**。

已落地并实机验证的部分：UIA 元素采集、单点探测、OCR 区域识别、融合与文本校正、
纯视觉分类规则，**以及覆盖层交互**（Alt+A 后悬停自动框住鼠标下的元素，单击即取）。

## 三条通道

| 通道 | 提供什么 | 覆盖 | 成本 |
| --- | --- | --- | --- |
| UIA（`IUIAutomation`） | ControlType、Name、物理像素矩形、可点性 | Win32 / WinForms / WPF / UWP / Electron / 浏览器 / Office | 零模型，几十 KB 代码 |
| PP-OCRv4 det/rec | 文本行框 + 文字 + 置信度 | 有字就准 | 已有（`ppocr`） |
| ONNX 检测模型 | 可点击区域、图标位置 | canvas / 游戏 / DirectUI 自绘 | 需训练 + 标注（第二期） |

**取舍依据**：UIA 一条通道就覆盖约 80% 的"按钮/输入框/文本"，而且是唯一给出**语义**
（是按钮还是输入框）的来源；纯视觉能框准位置但说不出类型。所以顺序是 UIA → OCR →
视觉，不是反过来。PixPin 那类工具的实际行为也接近这个结构。

被否掉的两条路：

* **OmniParser 式的纯视觉主管线**。语义靠 caption 模型补，一屏 0.6–0.8 秒、模型几百 MB，
  而且 `icon_detect` 继承 YOLO 是 **AGPL**，和本项目 Apache-2.0（明确允许闭源使用）冲突。
* **端到端多模态大模型**（Qwen-VL 之类）。一屏 1–3 秒、3 GB 显存，截图工具没有这个预算。

## 数据流

```text
按热键
  │
  ├─ 1. 元素快照（覆盖层创建之前！）      uielem::snapshot_targets(uielem::capture_targets(), 2500ms)
  │      句柄在热键那一刻同步取定；一次采多个窗口（父子去重）并合并，遍历走后台线程
  │      RawViewWalker + BuildCache，深度 32，父矩形在屏外就剪枝
  │
  ├─ 2. 抓屏                              screen::Frame::grab()
  │
  └─ 3. 悬停                              uielem::stack_at() 按几何包含往上爬

正式版目前**只走 1→2→3**：元素的名字全部来自 UIA。下面 4–6 是 `ui_scan` 自检里的
实验路径（OCR 增强），**还没接进产品**——接的话每次截图要多 2 秒和一份 OCR 引擎。

  ├─ 4. 按元素框裁切识别（准确率主来源）  ppocr::recognize_region()
  ├─ 5. 元素并集区域内 det 补漏（范围兜底） ppocr::detect_lines()
  └─ 6. 融合                              uielem::fuse()
```

**坐标约定**：全程虚拟桌面物理像素。渲染进程是 per-monitor v2，UIA 返回的
`BoundingRectangle` 已经是物理像素，和 `Frame` 天然对齐，不做任何 DPI 换算。

## 覆盖层接线（已接）

用户看到的行为：

| 操作 | 结果 |
| --- | --- |
| 悬停 | 自动框住鼠标下最细的一层：**元素 → 子窗口 → 顶层窗口 → 显示器**，气泡显示「按钮 · 最小化 46 × 30」 |
| 单击 | 把当前框住的元素直接当选区（不拖动就是"取这个控件"） |
| Enter | 选区阶段直接取元素进标注，等价于单击 |
| 滚轮 | 在两个图层级之间切：控件 / 窗口 / 显示器 |
| 气泡「复制文本」 | 把元素的 UIA 名称写进剪贴板（图标之类没名字的就什么都不做） |
| 气泡「复制信息」 | 复制 `类型 · 名称<TAB>x,y 宽×高`，一行，方便贴 issue 或者粘进表格 |
| 气泡「存图标」 | 元素框内的像素**原样**存成 PNG：`<截图目录>/图标_<名字>_<时间戳>.png`（46×30 就是 46×30，不缩放） |

复制完那一格就地变成「已复制」（1.2 秒），不另弹提示——视线本来就在气泡上。

**键盘导航做过后又砍了。** 曾实现过 Tab 循环 + 方向键空间跳转（约 120 行：阅读顺序表、
空间就近选择、独立于光标的选中态），实测能用，但它是给重度用户准备的增益功能——
鼠标悬停 + 单击已经覆盖全部用法。为它养一份 `kb_list` 副本、一套 `kb_*` 状态机和一个
"鼠标一动就交回指针模式"的隐式约定，不划算。**要加回来的话，git 历史里没有，得重写。**

实现要点：

* 快照在 `create_window` **之前**起（`start_element_snapshot`）：那一刻前台窗口还是目标
  应用，**一批窗口句柄先定下来**（`uielem::capture_targets()`），遍历丢给后台线程
  （`spawn_element_worker`），不拖慢覆盖层的出现。
* 线程只传 `isize`（`HWND` 不是 `Send`），采完 `PostMessage(WM_ELEMS_READY)`；
  覆盖层收到就 `detect(true)` + 重画一次——否则用户得先抖一下鼠标才看得见框。
* 悬停链仍是原来那条 `Vec<Target>`，元素只是被**塞到第 0 层**，所以滚轮换层级、气泡排版、
  单击取框这些既有逻辑一行没改。
* `elems.try_lock()` 抢不到锁就当作"这次没有元素"，悬停绝不阻塞在锁上。
* 开关沿用设置里的「悬停识别窗口/控件」（`detect_window`，默认开）；关掉则完全不采快照。

## UIA 通道的关键决策

1. **采集范围是"多个窗口"，不是"前台窗口"。** 这条是踩过用户反馈才改对的：只采
   `GetForegroundWindow()` 时，**任务栏永远采不到**——`Shell_TrayWnd` 从不激活，永远
   不是前台窗口；浏览器也常常不是前台（人在 IDE 里按 Alt+A）。现在一次采三样：

   * 前台窗口；
   * **光标下的窗口**（前台不一定就是它，悬停任务栏/未激活窗口时靠这个）；
   * **任务栏族**：`Shell_TrayWnd` / `Shell_SecondaryTrayWnd`（副屏）/
     `NotifyIconOverflowWindow`（托盘溢出，只在弹出时可见），用 `EnumWindows` 按类名收。

   实测（2560×1440，浏览器+IDE+任务栏同屏）：前台窗口 132 个元素、任务栏单独 31 个 /
   22ms、合并后 380 个 / 147ms，`输入框 地址和搜索栏`、`按钮 收藏夹`、`按钮 开始`、
   `按钮 … 已固定` 全都在。**不采桌面根**：那会触发桌面上每个程序建 a11y 树
   （Chromium 会因此拉起它的 accessibility engine），为了几个用户不会去悬停的窗口
   付这个代价不值。

2. **必须在覆盖层创建前取快照。** 覆盖层是 `WS_EX_LAYERED | WS_EX_TOPMOST` 全屏窗口，
   一旦显示，`ElementFromPoint` 命中的就是它自己。所有元素采集发生在覆盖层之前，
   覆盖层内只对快照做命中测试，不再跨进程调 COM（顺带把悬停延迟做到零）。
3. **专用 worker 线程 + MTA。** 跨进程 COM 在目标程序无响应时会卡 3–5 秒。
   worker 用 `COINIT_MULTITHREADED`（UIA 客户端用 MTA，少一层封送、不需要消息泵）。
   注意：超时**不靠遍历中途检查 deadline**——`FindAll` 是一次不可打断的整批调用，
   耗时已经付过，半路丢结果只会让元素框莫名其妙少一半。真正兜底的是调用方
   `recv_timeout` + 丢弃卡住的线程，遍历本身读的是本地缓存，有 `MAX_NODES` 封顶。
4. **预算给够，别把"慢"当"死"。** 221 个元素的窗口，`FindAll` + 过滤实测 967ms。调用方的
   `recv_timeout` 原本给 900ms，结果算完了却被判定超时、返回值被丢掉。现在给 1500ms。
   就算真超时也不致命：worker 仍会把结果写进共享数组并 `PostMessage` 让覆盖层重画，
   元素只是晚到，不是没有。
5. **卡死就丢弃线程。** 调用方 `recv_timeout`，超时置 `STUCK` 标记，下次调用换一个新
   worker（宁可泄漏一个线程，也不能冻住界面）。
6. **ControlView 而不是 RawView。** RawView 会把每个布局节点都吐出来（浏览器一屏
   2000+），噪声大到没法用；ControlView 只给真实控件，是"范围 vs 准确率"的平衡点。
   上限 `MAX_NODES=1500`。
7. **必须批量取，不能逐节点取。** 逐节点 `CurrentXxx()` 是每个元素 5–6 次跨进程往返，
   一个浏览器窗口就是几千次：实测 500ms 只走完 57 个元素（整棵树 117 个），元素框会
   "少一半"。改成一次 `FindAllBuildCache(TreeScope_Subtree, ControlViewCondition, 缓存请求)`
   连属性一起取回，再用 `CachedXxx()` 从本地读——122 个元素 336ms，比逐节点快一倍而且
   拿得全。缓存请求里把 `AutomationElementMode` 设成 `None`，不替每个元素握跨进程活引用。
5. **过滤三件套**：`IsOffscreen`、与虚拟桌面求交（滚动容器里滚出屏幕的元素矩形会是
   负几万，`IsOffscreen` 并不总能拦住）、面积不超过根窗口 90%（铺满的基本是背景）。
8. **单点探测取"最内层可交互"**：从 `ElementFromPoint` 往上爬，命中第一个
   Button/Input/Link/Tab/Menu/Cell 就停——点按钮里的图标时，图标只是 Image，
   真正的目标是外侧 Button。
9. **Name 清洗**：去 `(&S)` / `(E)` 加速键组、去 `&` 前缀、去尾部冒号、
   超长截断到 120 字（浏览器里一个 a11y"列表项"经常挂着整篇文章的正文）。

## 采集踩过的五个坑

这一节是血泪账，全部是实测踩出来、修好之后写下的。**动采集代码前先读一遍。**

1. **`FindAll(ControlView)` 拿不到布局层级。** Chromium 只把有语义角色的控件交给
   控制视图，页面内容被压平成 `元素 → Document`。换成 `RawViewWalker` 才有
   `元素 → 段落 → 块 → 列表 → 容器` 这样的完整链。
2. **`FindAll(RawViewCondition)` 也没用。** 条件只交给 provider 过滤，节点数几乎不变
   （357 vs 380）。RawView 的层级**只能靠 walker 一层层走**。
3. **`IsOffscreen` 在窗口失焦时整页说谎。** 浏览器不是前台时，Chromium 把整页元素
   标成 offscreen，一次实测扔掉 1817 个。**只信矩形**：`intersects(rect, 屏幕)` 判。
4. **BFS 深度给少了等于没采。** 页面正文在 `Document` 下面还有 8–12 层，
   `MAX_DEPTH` 必须给到 32。
5. **父子窗口重复采集 + 预算超时后返回空。** `Chrome_RenderWidgetHostHWND` 是
   `Chrome_WidgetWin_1` 的子窗口，采两遍直接顶穿预算；超时后调用方拿到空列表，
   表现就是"什么都不识别"。用 `IsChild` 去重子窗口，并把预算放到 2500ms。

另外：`AutomationElementMode_None` 会让 walker 遍历失效（只给缓存值、不给活引用），
整棵树只剩根节点。用 walker 就不能设这个模式。

## OCR 准确率：为什么能"保证"

原本的整屏识别有一个硬伤：`DET_LIMIT = 960`。4K 屏按下热键时，整屏被压到 1/4，
**12px 的界面文字在 det 阶段就已经糊掉，框都出不来**——这是截图 OCR 不准的主因，
换模型解决不了。

元素框已知之后，这条路就绕开了：

* **跳过 det，直接裁元素框送 rec**，框高 12px 会被放大到 48px（4 倍超分），
  这是准确率提升的主要来源（`ppocr::recognize_region`）。
* **多行元素先裁再 det**：段落、表格单元格不走单行 rec，而是裁出来跑完整流程，
  裁切后同样不受整屏 960 上限影响。
* **det 补漏也先裁区域**：只在元素并集范围内检，区域越小 det 越准。
* **CTC 置信度**：`rec_segment_scored` 给出逐字平均概率，用于文本取舍与低置信度过滤
  （低置信度的处理见下一节）。

### 反色重试：试过，零收益，**已删**

曾按"置信度低就反色重跑一次，救深色主题"实现了一版，并用对照实验验它（A 原图 /
B 整体反色 / C 反色+重试，10 个控件）：

| | 与原图一致 | 平均置信度 |
| --- | --- | --- |
| A 原图 | 9/10 | 0.68 |
| B 反色 | 7/10 | — |
| C 反色+重试 | 7/10 | 0.71 |

**重试触发 0/10 行。** 三个发现：

1. **PP-OCRv4 对极性基本免疫。** 四个纯文本控件（编辑/窗口/帮助/关于）反色前后全部读对，
   置信度反而略升（0.87→0.96）。反色对文本既不变好也不变坏。
2. **掉的两分全在图标上。** 最小化的横线反色后被读成 `1`，筛选读成 `T`——越救越糟，
   因为图标本来就不是文字。
3. 即便把阈值收到「≥2 字 + 置信度 <0.55」，也一次都没触发。

所以这套代码**已经删掉**了（连同 `to_tensor` 的 `invert` 参数、`ZHUXIA_OCR_NO_RETRY`
开关、那个对照实验的 example）。留着只是多一个分支和一份没人用的探针。

同一份数据的真用处是另一条：落不进任何控件的 OCR 行，置信度低于 0.5 直接丢
（`uielem::ORPHAN_SCORE`，有单测）。实测图标被当字读集中在 0.2–0.65、真实文本 ≥0.87，
0.5 两边都不挨着。

局限也得说清：这个实验是把浅色界面整体反色来模拟深色主题，只验证了"极性"一个变量；
真实深色主题还多了低对比度和次像素渲染，那是另一回事，**还没验**。

### 文本冲突时的淘汰规则（`pick_text`）

这是踩过坑才定下来的。第一版规则是"OCR 置信度 ≥0.85 就用 OCR"，实机立刻出问题：
按钮"最大化"的图形被读成 **"口"**、图标被读成 **"0"**，置信度还高达 0.95 以上，
把 UIA 正确的名字覆盖了。

| 类型 | 取值 | 依据 |
| --- | --- | --- |
| 输入框 | **OCR 优先** | 框里是用户输入的实际内容，比控件标签有用 |
| 文本区 | 两者中更长且 OCR ≥0.85 用 OCR，否则 UIA | UIA 的 Name 常被截断 |
| 图标 | **只信 UIA，OCR 一律丢** | 形状不是文字 |
| 其他可命名控件 | **UIA 优先**，仅当它以 `…`/`...` 结尾（截断）才用 OCR | UIA 的 Name 就是控件标题，本身是真值 |

一句话：**UIA 给语义，OCR 给像素读数；谁的活谁干，不互相"校正"。**

## 实测（Windows 11，8 核，浏览器 + 编辑器混合界面）

| 项目 | 数值 |
| --- | --- |
| 元素快照 | 122 个 / 336ms（其中 `FindAll` 314ms，debug 构建） |
| 单点探测 | 22–37ms |
| 单元素 rec | 约 22ms（100 个元素 2203ms） |
| 区域内 det | 236ms |
| 识别结果 | "编辑/窗口/帮助"加速键已清洗；"最大化"未被图标误读覆盖；`评估截图UI元素` → `评估截图 UI 元素` |

按元素逐条识别 22ms/条，全量跑一百个元素就是 2 秒——**不能这么用**。产品形态是
悬停/空格切换时只对当前元素识别一次（22ms），或者在覆盖层打开时后台预热逐个填。

## 层级：元素 + "包含它的更大元素"

PixPin 的文档写得很清楚（[基础截图](https://pixpin.cn/docs/screenshot/basics)）：

> **界面元素自动定位**：识别窗口中的按钮、输入框、图片、段落等界面元素。
> **上层元素**：向上滚动滚轮，选中**包含它的更大元素**；向下滚动回到更小的元素。
> **Tab**：在窗口和元素之间切换。

也就是说它的模型是「**元素 + 包含关系构成的层级**」，不是"一行卡片算一个块"。
我们照这个改，链是这样的（实测）：

```text
层级链 5 层：列表项[480x40] > 其他[480x220] > Chrome_RenderWidgetHostHWND[1463x1126] > WorkBuddy > 整块屏幕
```

**默认停在第 1 层（最小元素）**，滚轮向上逐级变大——和 PixPin 一致：先给最准的，
需要更大范围再滚。

### 之前错在哪

1. **`container()` 只认 Pane/Group/Custom/Window，把 `List` 漏了。** 网页里"一行卡片"
   的父容器通常就是一个 `List`，被当成匿名容器丢掉了——于是"更大的元素"根本不存在。
   现在 `List / Tree / Table / DataGrid / ToolBar` 都算容器。
2. 一度自己造假"块"（把等距元素按几何合并）。方向是错的：PixPin 给的是**真实存在的
   父元素**，不是猜出来的框。已经删掉。
3. 用 `GetParentElement` 爬父链太慢（每层一趟跨进程调用）。改成**几何包含**推导：
   父级 = 面积更大、且矩形包住当前元素的那个最小的元素。零额外 COM 调用。

### 相关设置与开关

| 项 | 我们 | PixPin |
| --- | --- | --- |
| 识别模式 | `detect_window` 设置；截图时 `Tab` 临时切"只认窗口" | 不检测 / 仅窗口 / 检测元素（默认） |
| 层级切换 | 滚轮（上=更大，下=更小） | 同 |
| 元素识别边距 | 未做 | 默认 0，−50–999 |

### 仍然做不到的

* **没有父容器的页面**：纯 `div` 布局（Chromium 不把它们交给 UIA）。这时链会直接从
  元素跳到窗口，中间那层"行"没有——只能靠视觉分割，而那条路已经砍了（见下节）。
* 纯 canvas 区域（Figma、在线表格）依然只是一个画布。

## 网页里的元素（Chromium / Electron）

**能识别，靠的就是 UIA。** 实测一个导航站页面（Chrome 系窗口）：

```text
266 个元素 / 205ms（冷）/ 187ms（热）  列表项 36 · 图标 49 · 按钮 3 · 文本 90 · 输入框 1 · 链接 87
链接 · BLOG 106x54 @632,127    链接 · 应用 77x54    链接 · 工具 78x54
链接 · 社区 78x54              链接 · 热榜 78x54    链接 · 排行 77x54
```

87 个页面链接、页面里的输入框和按钮全在。冷热两次完全一致（266/205ms vs 266/187ms），
所以**不存在「Chromium 懒建树、第一次给不全」的问题**——那次请求的 205ms 里已经包含
构建 a11y 树的时间。

Electron 应用同理：本项目自己的截图就是证据——WorkBuddy 的聊天正文（DOM）被读成
`文本`，侧边栏和标签页被读成 `按钮`/`标签页`。

### 那为什么之前"识别不到网页组件"

因为**采集范围**（见上面第 1 条）。网页元素一直能拿到，但只采前台窗口时：

* 浏览器不是前台（人在 IDE 里按 Alt+A）→ 整个页面都不在采集范围里；
* 只有浏览器恰好是前台时才碰巧能识别——所以体感是"有时行有时不行"。

改成「前台 + 光标下窗口 + 任务栏族」之后，光标停在网页上就一定能采到。

### 网页元素的真实限制

* **元素多**。`MAX_NODES = 1500` 是每个窗口的上限，普通页面 200–400 个很宽松；
  复杂单页应用（Gmail、Figma 这类）可能顶到上限，表现为**页面上半部分能识别、
  下半部分没有**。真遇到就把浏览器的上限单独放到 3000。
* **拿到的是 a11y 语义，不是 DOM**。看到的是 `链接`/`文本`/`按钮`/`输入框`，没有
  class、没有选择器、没有 id。对截图工具够用；要做自动化测试就不够。
* **深嵌套容器会被过滤**。`Kind::Other` 只在"有名字"时保留，网页里大量无名 div 会被丢掉——
  这是有意的，否则一屏全是看不见的方框。
* **纯 canvas 渲染的页面**（Figma/在线表格）在 a11y 里只是一个画布，识别不到格子。
  这类要么用视觉，要么靠页面自己暴露的 a11y 树（Figma 有，某些自研 canvas 没有）。

## 视觉通道：**暂缓，不做**（2026-11-24 决定）

结论：UIA + OCR 已经覆盖到"够用"的线，检测模型不划算。**除非出现下面任一条件，否则不
再往下推**：

* 有用户明确反馈"我要截微信/钉钉/游戏里的按钮，框不住"——且这个诉求出现频率够高；
* 或者 UIA 覆盖率的实测值明显低于下面这张表（不同 Windows 版本/应用生态可能不同）。

不做的主要理由，按重要性排：

1. **性价比**：模型要自标 2–3k 张 + 训练 + 导出 + 许可审查，换来的只是"自绘 UI 里**没有
   文字**的图标轮廓"。而有文字的地方，OCR 的 det 已经在兜底了。
2. **体验风险**：UIA 是"要么对、要么没有"，模型是"每次都可能框歪一点"。框歪的吸附比不吸附
   更烦人——用户手一抖就被拽到一个错的位置。
3. **失败模式对不上**：实测掉分全在图标上（见上一节），而图标恰恰是用户手动画框最不需要
   辅助的地方；真正难标的是密集控件区，那又是 UIA 的强项。

覆盖面实测（一个真实工作窗口，WorkBuddy）：

| 场景 | 现在能不能取到元素 | 靠什么 |
| --- | --- | --- |
| 标准 Windows 控件（按钮/菜单/输入框/列表） | ✅ 122 个元素，86 个带名字 | UIA |
| 浏览器 / Electron / Office / UWP | ✅ | UIA（Chromium 的 a11y 树） |
| 自绘 UI 里的**文字** | ✅ 有文本框 | OCR det + rec |
| 自绘 UI 里的**无文字图标** | ❌ 只有整窗口/子窗口的框 | —— |

也就是说缺口只有最后一格。这一格值不值 2–3 人月，答案是不值。

如果将来真要接，运行时选型和数据都在下面留了档，接的时候只需要：模型文件 +
一层 `Detector`（输入帧、输出 `Vec<Element>`）+ 在 `walk()` 之后并一次结果。
`evaluate` 不需要改——`fuse()` 按 IoU 去重，视觉框和 UIA 框天然能合。

### 真要接的时候的方案（留档）

* **模型**：YOLOX-nano 或 PP-PicoDet，Apache-2.0，640 输入，导出 ONNX。
* **不用** OmniParser 的 `icon_detect`（AGPL，与 Apache-2.0 冲突）。
* **不做** icon caption（Florence-2 那类），只出框，不出语义描述。
* **运行时**：`ort` crate + `load-dynamic`，从 exe 同目录加载 `onnxruntime.dll`，
  **默认 CPU EP**，DirectML 做成显式开关 + 空闲释放（实测数据见下一节，460MB 换 5 倍
  提速不划算）。session 常驻并在启动时预热一次空推理。
  **不碰 WinRT 的 `LearningModel`**——它线程亲和（`!Send`，只能 thread_local）、
  异步 `EvaluateAsync` 在 Win32 消息循环里会死锁、EP 不可控、精简版系统可能没有。
* **数据**：公开数据集（RICO/VINS/ScreenSpot）几乎都是手机或网页 UI，Windows 自绘
  控件得自己标 2–3k 张。这是整个功能最大的人力成本。

## 推理运行时实测（探针已随决定删除，数据留档）

做这个决定时写过 `ort_probe`，跑 PP-OCRv4 det 当负载。**探针已经删了**（视觉通道不做，
没必要为它养一个 15MB 的运行时依赖），数据留在这里；要复现按本节末尾的命令重建，半小时的事。

| 输入 | 后端 | 建会话 | 首帧冷启 | 稳态 | 常驻内存 |
| --- | --- | --- | --- | --- | --- |
| 640 | CPU | 58ms | 119–123ms | **43ms** | +24MB |
| 640 | DirectML | 397ms | 201–214ms | 7.4ms | +465–489MB |
| 960 | CPU | 59ms | 269–306ms | 102–110ms | +29MB |
| 960 | DirectML | 402ms | 198–1493ms | 15ms | +590–644MB |

`[dll] 加载 + 环境构建：18–21ms`，`DirectML：可用`。

四条结论，都是拿数说话：

1. **ORT CPU ≈ 现有 WinML CPU**（960 上 102–110ms vs 89ms）。迁移不掉性能，白拿
   EP 可控 + `Session` 是 `Send`（不用再 thread_local）。
2. **DirectML 的代价在启动和内存，不在推理**：建会话 400ms、常驻 465–590MB，
   换 6–14 倍提速。对"常驻小工具"这个定位，这个内存账算不过来。
3. **640 尺寸 CPU 43ms 已经进得了 200ms 预算**，所以视觉通道默认 CPU EP；DML 做成
   用户显式开启，并且空闲自动释放（复用 OCR 的 `unload_if_idle` 思路）。
4. **冷启动 120–300ms，必须预热**：启动后台线程建会话 + 跑一次空推理，
   不能等用户按 Alt+A 才建。

踩坑：`GraphOptimizationLevel::Level3` 在 ORT 的 C 枚举里**不是合法值**（只有
0/1/2/99），要写 `All`，否则直接 `graph_optimization_level is not valid`。
`ort` 的 `with_*` 返回的错误类型带着"可恢复的 builder"，`?` 串不起来，得先
`map_err` 成字符串。

## 内存与开销（这个功能到底占多少）

要知道"是不是过度设计"，先看账。实测（`ui_hover_check` 里打的点，175 个元素）：

| 项 | 占用 | 什么时候释放 |
| --- | --- | --- |
| UIA 通道：worker 线程 + `uiautomationcore` 映射 + 元素表 | **约 2MB**（1.7–3.0 波动） | 常驻（线程空闲时不干活） |
| 元素表（450 个元素左右，含任务栏/浏览器页面） | ~200KB | 覆盖层关闭即释放 |
| 整屏冻结帧 `Frame`（2560×1440×4） | 14.7MB | 覆盖层关闭即释放，**原本就有** |
| OCR 引擎（WinML 会话） | ~200MB | 已有空闲自动释放，**原本就有** |
| 视觉检测模型 | 0 | 不做 |

两点结论：

1. **这个功能本身几乎不占内存**，1.7MB 里绝大部分还是 `uiautomationcore.dll` 的代码映射
   （文件页，不占私有提交），元素表只有一百多 KB——400 多个元素时测到 1.2–2.3MB，
   说明这钱不是花在元素上。真正的内存开销在"冻结帧 + OCR 引擎"，
   那两项跟本功能无关，是截图本身就有的成本。
2. **不值得为这 1.7MB 加"空闲卸载 UIA"的机制。** 相比 OCR 的 200MB 它是个零头，
   加一套空闲回收只会让代码更绕——这正是要避免的那种复杂化。

真要继续压下常驻内存，该动的是 `Frame`（可以让 OCR 直接从 DIB 读，不必再拷一份）
和 OCR 引擎的驻留策略，不是这里。

## 已知限制

* **自绘 UI 的语义天花板**：微信/QQ/钉钉大量 DirectUI 自绘，UIA 只吐一个空 Pane。
  视觉能框准位置，但说不出是按钮还是输入框。这是上限，不是 bug。
* **提权不对称**：进程以管理员运行时读普通窗口没问题，反之不行；UIPI 还会挡住
  向更高完整性级别窗口的模拟输入。`ZHUXIA_NO_ELEVATE=1` 调试时这块会大面积失效。
* **远程桌面 / DRM 窗口 / 全屏独占游戏**：截图本身就是黑的，无从谈起。
* **UIA 实现质量参差**：`ElementFromPoint` 对 WinUI3 / WebView2 的表现逐版本变化，
  得按程序实测，不能默认一次写对所有。
* **不是 OCR 的替代**：长文本提取仍走 `Ctrl+O`；元素识别给的是框和短文本。
* **前台窗口是控制台/终端时，那一份几乎是空的**（conhost 的 a11y 树没什么东西）。
  这时只靠"光标下的窗口 + 任务栏"兜着。正常使用（前台是真应用）不会遇到。
* **副屏任务栏**靠 `Shell_SecondaryTrayWnd` 收，但极端情况（任务栏设成自动隐藏）下
  它可能不可见、采不到——`IsWindowVisible` 会把它挡掉。

## 收尾清单（视觉通道已砍，只剩这些）

按性价比排，都是小活：

1. **真实深色主题验证**：反色实验只验了极性，深色主题的低对比度还没验，需要真机截图。
   这是唯一可能有真 bug 的地方。
2. **元素级导出**：把同批元素的清单导出 JSON/CSV（`Element::info_line()` 已是半成品），
   给自动化测试当基线。
3. **多选**：Shift 累积选中多个元素一起复制——但现在连键盘选中都砍了，这条得先有选中态。
4. **别做**：给自绘 UI 补 OCR 文本框当悬停目标——技术上可行，但 `ppocr` 的引擎是
   `thread_local`，后台快照线程会额外起一份 WinML 会话（约 +200MB），为了最后一格缺口
   花这个内存不值。
5. **别做**：给 UIA 加"空闲卸载"。省 1.7MB，换来一套线程回收机制，纯亏。

## 构建注意

本机 PATH 里的 `rustc` 是 FlyEnv 的裸工具链（`C:\Program Files\FlyEnv-Data\env\rust`），
它的 sysroot 里**没有 std**，直接 `cargo check` 会报
`can't find crate for std`（doctest 也一样，因为那个失败是 `rustdoc` 引起的）。用 rustup 的那套：

```bash
RUSTC="$HOME/.cargo/bin/rustc" RUSTDOC="$HOME/.cargo/bin/rustdoc" \
  cargo check -p capture --all-targets
```

探针需要 OCR 模型（`target/debug/examples/ocr/` 下放 `det.onnx` / `rec.onnx` / `keys.txt`），
没有模型时只输出元素框，不会报错。

要量推理运行时（只在真打算接模型时才需要）。探针代码已删，重建步骤：新建
`examples/ort_probe.rs`，dev-dependency 加 `ort = { version = "2.0.0-rc.15",
default-features = false, features = ["load-dynamic", "directml"] }`，运行时：

```bash
curl -L -o ort.nupkg https://www.nuget.org/api/v2/package/Microsoft.ML.OnnxRuntime.DirectML/1.20.1
unzip -j ort.nupkg "runtimes/win-x64/native/*" -d target/debug/examples/ort
```

两个必踩的坑：`GraphOptimizationLevel` 要写 `All`（`Level3` 不是 ORT 的合法枚举值，
会报 `graph_optimization_level is not valid`）；`ort` 的 `with_*` 返回的 `Error<T>`
带着"可恢复 builder"，`?` 串不起来，得先 `map_err` 成字符串。

排查采集时可以 `set ZHUXIA_UIA_DUMP=1` 再启动正式版：每次截图会把元素清单
（类型/名字/矩形）写到 `<exe>/uia-dump.txt`，配合 `uia_tree.exe` 对比最直接。

界面自检（会真的弹一次全屏覆盖层并自动关掉，产物是 `ui-hover-check.png`）：

```bash
cargo run --release --example ui_hover_check
# 点一下气泡上的「复制文本」/「复制信息」，验证真的点得动：
cargo run --release --example ui_hover_check -- --click 1895,170
# 存图标（第三格），产物在截图目录里：
cargo run --release --example ui_hover_check -- --click 2035,170
```
