## 三、潜在 bug 与异常路径

### 3.1 GitHub 目录浏览没有分页（P1）

`crates/imgbed/src/providers/github.rs:225`（`list_dirs`）和 `:240`（`list_images`）
都只发一次 `GET {repo}/contents/{dir}`，没有 `page`/`per_page`，也没有翻页循环。

- **影响**：GitHub Contents API 单次最多返回 **1000 条**。按 `{yyyy}/{MM}` 分目录时不容易撞上，
  但只要有人把图片平铺在一个目录里（或上传历史久了没分目录），**超出部分是静默丢的**——
  界面显示不全，用户无从判断是真没有还是没取到。
- **建议**：用 `Link: rel="next"` 头或 `per_page=100&page=N` 翻页，直到返回空数组；
  同时在 UI 上标注"已列出 N 项"。

### 3.2 可重试错误没有重试（P1）

承接第 6 条。`github.rs:115/122/124`、`s3.rs:236`、`custom.rs:202` 都标了 `retryable`，
但 `queue.rs` 的 `run()` 收到 `Err` 直接记结果。

- **影响**：GitHub 409（同名文件刚被创建）、429（限流）、5xx 全部一次失败。
  限流时用户会看到"上传失败：GitHub 限流"，而其实等几秒就好。
- **建议**：`queue.rs` 加最多 3 次、指数退避（200/600/1800ms）的重试，只对
  `retryable == true` 生效；重试时保留同一个文件名，避免产生两份。

### 3.3 `ACT_SLOT` 是单槽（P2）

`crates/capture/src/ocr.rs:118`。翻译/AI 的结果通过一个
`Mutex<Option<(u8, Result<String,String>)>>` 回投。

- **影响**：连点「翻译」再点「AI 整理」，两个线程都会写这个槽：先完成的结果被覆盖、
  弹两次 `WM_ACT_DONE`，第二次取到的是同一个载荷。提示文案跟着载荷走不会串，
  但**先完成的那次结果丢了**。
- **建议**：槽里带上请求序号，`WM_ACT_DONE` 只在序号等于"当前请求"时才应用；
  或者按 `act` 分槽。

### 3.4 表格识别在 UI 线程跑 OCR（P2）

`crates/capture/src/ocr.rs:562 run_table()`。`Canvas` 握 GDI+ 句柄不是 `Send`，只能在 UI 线程重建。

- **影响**：识别期间窗口 0.3–1.5 秒无响应（大图更久）。虽然先画了一句"表格识别中…"，
  但 Windows 超过 5 秒会判"未响应"。
- **建议**：把裁切后的**像素**（`Vec<u8>`，是 `Send`）送到工作线程，在那边新建 Canvas 再识别；
  成功后再回投文本。`run_table` 现在持有 `doc_px` 拷贝，改造成本不高。

### 3.5 每次 OCR 复制整图像素（P2）

`crates/capture/src/overlay.rs:1872`：

```rust
let px = Some((doc.w, doc.h, doc.pixels().to_vec()));
```

- **影响**：全屏 OCR（2560×1440）一次复制约 **14 MB**，普通选区 1 MB 以内。
  这发生在按键响应的同步路径上。
- **建议**：改成惰性——只在用户点「表格」时才复制，或者把 `doc` 用 `Rc<Canvas>` 共享
  （窗口与覆盖层同线程，`Rc` 够用）。

### 3.6 采集配额静默截断（P2）

`crates/capture/src/uielem.rs:56-58`：`MAX_NODES=4000`、`MAX_DEPTH=32`、`MAX_SIBLINGS=200`。

- **影响**：超限时只写一条 `节点配额用尽` / `兄弟过多` 的日志，用户看不到。
  表现是"某些区块框不出来"，但没有可见提示，排查只能翻日志。
- **建议**：超限时在覆盖层的提示条上加一个小角标（如"元素已截断"），
  或至少把这条日志提到 `warn` 并带上窗口标题。

### 3.7 `unsafe impl Send` 无约束说明（P2）

`crates/zx-ui/src/painter.rs:44` `unsafe impl Send for Canvas {}`，
以及 `capture/src/pin.rs:34`、`capture/src/record/mp4.rs:43`、`capture/src/screen.rs:29`、
`gesture/src/overlay.rs:73`。

- **成因**：这些类型内部是 GDI+/DIB 句柄，有线程亲和性，`Send` 只是为了放进
  `Box`/`Arc` 跨线程**持有**，不代表可以跨线程**使用或释放**。
- **风险**：现在没人这么用，但编译器不会拦——将来谁把一个 `Canvas` 丢进线程池，
  表现会是随机崩溃或资源泄漏，且极难定位。
- **建议**：每处加 `// SAFETY:` 注释写清"只允许移动所有权，Drop 必须回到创建线程"，
  并用一个 `PhantomData<*mut ()>` 之类的手段限制（或提供 `into_thread_bound()` 包装）。

### 3.8 `&'static mut` 可能别名（P2）

`clipboard/src/panel.rs:2059`、`taskmon/src/detail.rs:920`、`taskmon/src/dialogs.rs:87`、
`capture/src/record/mod.rs:847` 都是：

```rust
fn get(hwnd: HWND) -> Option<&'static mut T>
```

- **风险**：同一个 `hwnd` 在嵌套调用里拿两次，就是两个 `&mut T` 指向同一对象——**技术上属于 UB**。
  目前靠"消息处理里不重入"这个约定在兜，但没有东西强制它。
- **建议**：改成 `RefCell` + `&T`/`borrow_mut()`，重入会 panic 而不是静默产生别名，
  或者用 `Cell<Option<Box<T>>>` + 回调式 `with_state(hwnd, |st| ...)`。

## 九、第二批整改（2026-11-26 01:40）

### 3.4 表格识别阻塞 UI —— **实测后降级为 P3**（原判 P2）

原报告写"0.3–1.5 秒无响应"，那是估的。实测（debug 构建，含建会话预热后）：

| 规模 | `table_markdown` |
| --- | --- |
| 3×5（15 格，720×300） | 140 ms |
| 5×10（50 格，1200×800） | 407 ms |
| 6×20（120 格，1600×1100） | 612 ms |

release 还会更快，典型表格在一两百毫秒量级——远低于 Windows 判定"未响应"的 5 秒。
而且这条路径已经先画了"表格识别中…"再阻塞，用户有反馈。

**结论：不做线程重构。** 代价对比很清楚：

- 把 OCR 搬到工作线程，要么多开一份会话（**实测引擎占 87 MB**，`7MB → 94MB`），
  要么把引擎改成常驻工作线程、所有入口走任务队列——后者要重排
  `recognize` / `recognize_region` / `detect_lines` / `table_markdown` 四条路径，
  而它们现在都在同一线程上跑得好好的。
- 收益是省下两百毫秒的输入延迟。**不划算。**

留了 `docs` 里的这条实测数据，以后有人想改先看这张表。

### 2.9 taskmon 补测试（9 → 20）

审计说"它算的百分比用户天天看，基本没有覆盖"。补的时候发现测试点不在采样器里
——采样器全是 Win32 调用，真正决定显示数字的是两层纯函数：

**① `zx_core::fmt`（11 个格式化函数，原本零测试）**

任务栏上每个数字都从这里出来：`42%`、`1.2 MB/s`、`3 天 04:15:22`、`61°C`、
`100 Mbps`。补的 11 条专门钉边界：`1023/1024` 进位点、负数（计数器回绕）、
`NaN`（GPU 驱动不报温度）、0、超长 uptime。**没有发现 bug**，格式全对。

**② 采样里的占用率公式**

`1 - 空闲/总计` 在三个地方各写了一遍（CPU 总体、单核、磁盘），字面不同、容易各错一处。
抽成 `sampling::busy_pct(idle, total)`，配 4 条测试（满载/全空闲/无时间推进/计数器抖动）。

顺手修了一个真问题：单核与磁盘的增量是裸减法
（`c.kernel - p.kernel`），而核心被 park/unpark 时计数器可能回退，
**debug 构建会直接 panic**。全部改成 `saturating_sub`。

**③ 详情面板的设备行**（`detail.rs` 7 条）

`mem_pair`（驱动不报显存总量时不能变成 `2.00 GB / 0 B`）、`disk_kind_line`（未知项
不能留 `SSD ·  · `）、`disk_letters`（没盘符时不能是空字符串）、`short_gpu`
（必须按字符截断，按字节会切出半个汉字直接 panic）。

所以 taskmon 从 9 条到 20 条，顺手给 zx-core 加了 11 条。

### 2.10 `save()` 全量重写 —— **实测后换了靶子**

审计的原话是"每复制一次重写整个历史文件"。先量，再决定改什么
（`cargo test -p clipboard --test save_cost -- --ignored --nocapture`）：

| 历史规模 | 加密 | 写盘 | 合计 |
| --- | --- | --- | --- |
| 1000 条 × 200B（0.25MB，**默认上限满**） | 3.45ms | 0.63ms | **4.08ms** |
| 20 条 × 512KB（10MB） | **572.97ms** | 3.27ms | **576.25ms** |

结论反过来了：**"整份重写"本身不是问题**——默认上限下满打满算 4ms，而且跑在
采集线程上，不挡 UI。真正的坑是**单条没有体积上限**：复制一个大日志文件之后，
这一条会永远躺在历史里，让**之后每一次复制**都掏 576ms（DPAPI 约 57MB/s），
而且全程握着 store 的锁，面板这时候打开就卡住。

修法（`store::MAX_PERSIST_BYTES = 1 MiB`）：

- 正文 + 富文本超过 1MB 的记录**照常进内存**，粘贴、搜索、置顶都不受影响；
- 只是不写进历史文件（重启后消失），落库时打 `#不保存` 标签，面板里能看见；
- `save()` 落盘前过滤，并记一条 info 说明有几条因此没写。

没做"防抖写盘/后台写线程"：那会引入"退出时丢最后一条"的窗口，而实测证明
常规情况本来只要 4ms，不值得。

### 2.11 `unsafe impl Send`（5 处）—— 把真实原因写清楚

审计说"没有约束说明"。查下来这 5 处的**真实用途都不是"可以跨线程用"**，
而是"要能放进 `static Mutex<T>`"（`static` 要求 `T: Send`）。这个区别很关键：
按"可以搬线程"去理解，就会真的把 `Canvas` 挪到别的线程去画。

所以注释统一按事实写（`painter.rs` / `pin.rs` / `screen.rs` / `gesture/overlay.rs`；
`mp4.rs` 原本就对——`IMFSinkWriter` 确实是 free-threaded 的 MTA 对象）：
**`Send` 只为过 `static` 的门槛，创建/使用/销毁仍在同一线程**，并写明违规
（GDI+ 按线程初始化，跨线程用会随机崩在 GDI+ 内部，debug 也未必报错）。

### 2.12 配额截断可见化

原来截断只写日志（`节点配额用尽` / `兄弟过多` / `到达截止时间`），用户看到的是
"这个页面框不上去"，会以为程序坏了。

现在：`walk()` 判定被截断时置全局标记，悬停气泡的标签后面多一句
**`· 结构已截断`**——性质从"程序坏了"变成"这个页面太大"。屏幕外剪枝和
"铺满窗口"是正常优化，不算截断（有测试钉住）。

顺手把三个原因字符串收成常量。原来是"记的地方和判的地方各写一遍字面量"，
改一处就会静默失配，界面上永远不显示。

## 十一、`&'static mut` → 借用守卫（2026-11-26 08:5x）

上一轮我写过"thread-local 深度计数会产生误报，分不清同时存活和先后使用"。**这句是错的**，
先更正：计数器的生命周期跟着守卫走，`if let Some(p) = get(h) { ... }` 结束时守卫就 Drop，
所以先后两次取是 `1 → 0 → 1`，**不会累积**；只有两个守卫同时存活才是 2，那正是 UB。

### 做法

新增 `zx_core::borrow::Ref<T>`：借用守卫，`Deref`/`DerefMut` 到 `T`，构造时给调用方传入的
thread-local 计数器加一、`Drop` 时减一，debug 构建里 `assert!(n == 1)`。四个访问器改签名：

| 模块 | 访问器 | 调用点 |
| --- | --- | --- |
| `clipboard/panel.rs` | `panel_of` | 16（wndproc 各分支 + `paste`） |
| `taskmon/detail.rs` | `get` | 4 |
| `taskmon/dialogs.rs` | `get` | 4 |
| `capture/record/mod.rs` | `cache` | 1 |

因为守卫 `Deref` 到 `T`，调用点几乎不用改——只是绑定要加 `mut`（`Some(mut p)`），
以及一处字段分裂借用 `p.canvas.resize(p.w, p.h)` 要先把尺寸取出来。

### 抓到一个真的

`Panel::paste(&mut self, ...)` 的失败分支里写着：

```rust
if !paste_entry(...) {
    show(true);
    if let Some(p) = panel_of(self.hwnd) {   // ← self 就是那个 &mut Panel
        p.toast("粘贴失败：内容已不可用");
    }
}
```

这就是标准的双 `&mut`：`self` 还活着，又造了第二个。改成 `self.toast(...)`。

**这是这套守卫唯一抓到的实例**，其余 24 个调用点都在 wndproc 的 match 分支顶层，
一次只有一个守卫存活。

### 覆盖边界（写进代码注释了）

`show_now` / `hide_now` 直接走 `PANEL` 的裸指针（它们要处理"还没建出面版"的情况），
**不在计数之内**。所以在已经持有守卫的方法里调用 `show()`，守卫看不见——
这类调用只有 `paste` 一处，已改。后续别再加。

要彻底消掉"方法里调模块级函数"这条路，得把 `Panel` 改成 `Rc<RefCell<..>>` 或者
把状态搬进结构体字段，那是另一个量级的改动，收益不明显（剩下的都是单线程顺序调用）。

`#[should_panic]` 验证嵌套会被断言抓住），`clippy --workspace --all-targets` 零告警。
